# Coolify rollback operations

> Migration note: this document describes the retained `v1.0.0` rollback runtime. Cloudflare Workers Static Assets is the active migration target, and routine releases must follow [DEPLOYMENT.md](./DEPLOYMENT.md). Do not resume, rebuild or delete the preserved Coolify workload without explicit operator approval.

This runbook explains the portfolio's Coolify lifecycle on the existing Windows Docker Desktop host. It distinguishes expected Coolify infrastructure from application deployments so generated names and temporary build artifacts are not mistaken for duplicate portfolio instances.

## Operating model

```text
Git commit
  └─ Coolify Dockerfile build
       └─ image: <application-uuid>:<git-sha>
            └─ container: <application-uuid>-<deployment-id>
                 └─ internal port 3000
                      └─ Traefik Host rule on port 80
                           └─ Cloudflare Tunnel
                                └─ public HTTPS hostname
```

The UUID and numeric deployment suffix are generated by Coolify. They are deployment identifiers, not branch names and not evidence that Codex owns the commit. Every deployment builds an immutable image for one Git revision, starts a replacement container, waits for health, and then routes traffic to the healthy revision.

They are not portfolio builds. The other named containers on the host belong to separate homelab services such as Nextcloud, Matrix, Immich, Karakeep and Glance.

1. `rahul-portfolio-rc` — the actual portfolio candidate.

The `whoami` service is not a portfolio dependency. Retire it from the Coolify project after the final portfolio host rules and rollback path are verified. Delete the Coolify resource through the Coolify interface; do not remove its generated container directly in Docker Desktop because Coolify may recreate managed resources.

## Simplified standalone artifact

`npm run build` now produces one self-contained `.next/standalone` directory:

1. `next build` traces the minimum server runtime.
2. `postbuild` copies `public/` and `.next/static/` into the standalone directory.
3. `npm start` runs `.next/standalone/server.js` directly.
4. The Docker runner copies the standalone directory once and runs the same `server.js`.

This removes the unsupported `next start` path and keeps local, CI, Docker and Coolify startup behavior aligned.

## Domain transition

The temporary Coolify route currently proves only that Traefik can reach the old candidate. For production:

1. Deploy the final reviewed commit while keeping `portfolio-rc.parmar.homes` available for validation.
2. Require the temporary deployment to become healthy with zero restarts.
3. Run the 29-check deployment contract against the temporary HTTPS hostname.
4. Add `http://rahulsinghparmar.site` and `http://www.rahulsinghparmar.site` to the Coolify application so Traefik creates both HTTP Host rules.
5. Route both Cloudflare public hostnames to the existing tunnel origin at `http://localhost:80`.
6. Redirect `www` to the canonical apex at the Cloudflare edge.
7. Remove the Coolify `localhost` diagnostic domain after the production Host rules pass.
8. Keep the temporary hostname during stabilization; remove it only after rollback evidence is recorded.

HTTP inside Coolify is intentional. Cloudflare terminates public TLS. Do not expose container port 3000, point the tunnel directly to the application container, or request a second Coolify certificate through the tunnel.

## Normal deployment workflow

1. Commit the reviewed tree and push `main` from Rahul's Git identity.
2. Require the GitHub quality workflow to pass for the exact commit.
3. In Coolify, open the application and select **Deploy**.
4. Confirm the deployment log checks out the intended full Git SHA.
5. Wait for container health; do not repeatedly click Deploy while a build is running.
6. Verify the temporary hostname before changing production routing.
7. Run the external deployment contract after the production hostname is connected.
8. Inspect application, Traefik and tunnel logs during stabilization.

Each deliberate deployment creates a new commit-tagged image. Multiple rapid Deploy clicks create multiple build attempts and are the most common reason the deployment list looks random. One reviewed commit should produce one deliberate manual deployment during the first release.

## Safe diagnostics

From the repository:

```powershell
npm run quality:check
npm run build
npm start
npm run deployment:check -- http://127.0.0.1:3000
```

From the Coolify host:

```powershell
& C:\Docker\coolify\maintenance\Manage-Coolify.ps1 Health
docker ps --filter label=coolify.type=application --format "table {{.Names}}\t{{.Image}}\t{{.Status}}"
docker system df
```

To test a Traefik route locally without changing DNS:

```powershell
Invoke-WebRequest -Uri http://127.0.0.1 -Headers @{ Host = "portfolio-rc.parmar.homes" } -UseBasicParsing
```

Do not print full container environments, `.env` files or Coolify database rows into logs; they may contain credentials.

## Cleanup policy

- Keep the current healthy and previous known-good application revisions during release stabilization.
- Remove the obsolete `whoami` resource through Coolify after production routing passes.
- Let Coolify retire deployment containers; do not delete UUID-named containers manually.
- Use the existing scheduled cache optimizer instead of ad-hoc `docker system prune` commands.
- Never prune volumes as part of a portfolio release. The portfolio is stateless, but the same Docker host contains stateful services.
- Review image retention only after the new revision is healthy and rollback is proven.

## Failure signals

Stop the release if any of these occurs:

- the deployed Git SHA differs from the reviewed commit;
- the container never reaches healthy or restarts unexpectedly;
- Traefik returns 404 for the expected Host header;
- static CSS, JavaScript or `/images/rahul.webp` returns anything other than HTTP 200;
- the deployment contract is not 29/29;
- the public hostname bypasses Cloudflare or reaches the old revision;
- repeated 5xx responses, OOM kills or sustained resource throttling appear.

Rollback by selecting the previous healthy Coolify deployment or redeploying its exact commit SHA. No database or volume rollback is required for this application.
